## Summary

Three confirmed code defects were fixed:

- Maya `PATCH /owner/spot-request` updated the user with an empty field mask and
  empty `UserName`, producing a 500.
- The home-page and SRP search box read `location.center` when Mapbox returned a
  null selection, producing the main `/` JavaScript alert.
- The search portal read `coordinate[0]` when a typed latitude/longitude value
  was invalid, producing a search-portal JavaScript alert.

Two additional frontend sources were reduced:

- Mapbox geocoding is no longer called with an empty or unencoded query.
- The search portal no longer calls authenticated endpoints before Firebase auth
  and the user role are ready.

The remaining alert volume is mostly not new application regressions. It comes
from expected integration failures, per-trace alert facets, stale deployment
chunks, network timeouts, and a few unfixed page-level defects. The current
legacy conditions are not managed by `observability/newrelic/terraform`, so the
noise changes below are recommendations, not applied changes.

## Noise reduction

These changes would make every alert represent a distinct action.

1. **Remove per-trace facets from the dev 5xx condition.** Keep `traceId` as
   event context, but facet on `transactionName` and `error.message`. Use
   `FACET transactionName, error.message`. This turns 104 mostly per-trace
   incidents into a small number of endpoint/error issues.

2. **Stop faceting frontend errors by user agent and full URL.** Use
   `FACET errorClass, errorMessage, route_name` instead of
   `errorClass, errorMessage, pageUrl, userAgentName, userAgentOS, deviceType`.
   If `route_name` is missing on the first load, add a low-cardinality route
   attribute to initial page events rather than falling back to the full URL.

3. **Move deploy-asset failures to a separate condition.** Dynamic import and
   CSS preload failures after a deploy are expected for tabs left open across a
   release. Alert only when the rate stays high outside a deploy window, and
   group all `chunk-load` errors into one issue.

4. **Split real exceptions from network timeouts.** Keep `Network Error` and
   `timeout of ... exceeded` in a latency/reachability condition, not in the
   same condition as application exceptions. They have different owners and
   different fixes.

5. **Keep 4xx out of JavaScript alerting.** The current exclusion is correct.
   Do not remove it when changing the facets.

6. **Fix or suppress the aggregate log alert.** `Error log count` fires on
   expected messages: `API failed with error` 600, `Whatsapp message not found`
   370, and `MakeHttpCall: non-2xx response` 97 in 7 days. Add structured
   `message`, `endpoint`, and `status` fields, then alert on unexpected
   message/endpoint pairs. At minimum exclude `Whatsapp message not found` and
   `Ping received`; keep the rest visible in a low-priority integration
   condition until they are classified.

7. **Consolidate duplicate 5xx conditions.** Production has both
   `maya 5xx errors` and `maya any 5xx by endpoint`, and dev has the full-detail
   condition. Keep one production endpoint condition and one dev diagnostic
   condition whose facets are stable. Route the aggregate to the service-level
   burn alert instead of paging twice.

8. **Do not alert on missing session storage.** `sessionStorage` denial is a
   browser privacy setting. Catch it and continue without persistence.

9. **Manage these legacy conditions in Terraform.** The current conditions live
   outside `observability/newrelic/terraform`, so an apply cannot correct UI
   drift. Import them or replace them with Terraform-managed conditions before
   tuning thresholds.

## Suggested thresholds

- Backend 5xx by endpoint: critical when error count is above 0 for 5 minutes,
  warning after 5 errors in 15 minutes. Keep one issue per endpoint.
- Frontend application exceptions: critical after 5 occurrences of the same
  `errorClass`, `errorMessage`, and `route_name` in 15 minutes. Keep 4xx excluded.
- Stale deploy assets: warning when more than 20 chunk-load failures occur in
  15 minutes, and only outside a deployment marker window.
- Network timeout/error: warning when the rate is more than twice the 7-day
  baseline for 30 minutes.
- `Error log count`: critical only for new or increasing unexpected message
  signatures; expected integration messages go to a daily digest.
